# OR1011: possible N+1 (EF Core navigation not loaded by the query)

**Default:** hint (dots under the code, not in Problems). Setting `refyntra.rules.OR1011`.
**Kind:** heuristic. It reasons about source code only; it never builds the EF Core model or looks at a database.

## What it reports

A navigation property of an EF Core entity is read for every result of a query that does not load it:

```csharp
foreach (var order in db.Orders.Where(o => o.Total > 0).ToList())
    Console.WriteLine(order.Customer!.Name);   // OR1011 on order.Customer
```

Without lazy loading, `order.Customer` is **not loaded** by this query: it is `null` (or an empty collection), unless
the same context happened to track those customers already. The usual "fix" that follows — loading the navigation for
each order (`Entry(order).Reference(…).Load()`, or a query in the loop) — costs one database round trip per result:
the N+1 pattern. Loading it with the query is one round trip (or one per `Include` with split queries).

So the result means: *this navigation is probably not loaded here; if you need it, load it with the query.* It does
not claim that N+1 queries already happen: with lazy loading off they do not, the data is simply missing.

## When it is reported (all must hold)

- The read is `x.Nav` where `x` is the variable of a `foreach`, or the parameter of an in-memory `Select`,
  `SelectMany` (`System.Linq.Enumerable`) or `List<T>.ForEach` lambda.
- The loop source is provably an EF Core query from the same function: written inline, or a local that is assigned
  only once, from that query (`await` and `ConfigureAwait` are looked through).
- The query starts at a `DbSet<T>` of a DbContext (`db.Orders`, `db.Set<Order>()`) and every operator after it is a
  known filter, sort, paging, tracking or materialization operator (`Where`, `OrderBy…`, `Skip`, `Take`, `Distinct`,
  `AsNoTracking…`, `AsSplitQuery`, `TagWith`, `IgnoreQueryFilters`, `ToList(Async)`, `ToArray(Async)`,
  `AsEnumerable`, …) or `Include` / `ThenInclude`.
- The element type of the loop is the query's entity type, and `Nav` is a reference or collection navigation to an
  entity that the same DbContext maps with a `DbSet<T>` property.
- No `Include` of the query names `Nav` (lambda, filtered include or string path).

## When it stays silent

- Any projection or other operator in the query (`Select`, `GroupBy`, `Join`, `FromSql…`, a method of your own):
  the query shape is not proven.
- The loop source is a parameter, a field, a property, or a local written more than once.
- Lazy loading is possible: the project references `Microsoft.EntityFrameworkCore.Proxies`, or the entity has an
  `ILazyLoader` (or `Action<object, string>`) field, property or constructor parameter.
- The navigation is configured with `AutoInclude()` anywhere in the project (matched by name; an `AutoInclude()` the
  rule cannot read silences the rule for the project).
- Owned types (`OwnsOne`/`OwnsMany`) and complex types: they are not `DbSet` entities and are loaded with their owner.
- `[NotMapped]` properties, computed properties (a getter with a body), writes (`x.Nav = …`), `nameof(x.Nav)`.
- The loop body loads explicitly (`Entry`, `Reference`, `Collection`, `Load`, `LoadAsync`, `Find`, `Include` inside it).
- Inside the query itself (`db.Orders.Count(o => o.Lines.Any())` is translated to SQL).
- Generated code; `#pragma warning disable OR1011`; `[SuppressMessage("Refyntra", "OR1011")]`.

Known false positives: the navigation was loaded by an earlier query on the same tracking context (relationship
fix-up), or you really want it unloaded. Known false negatives: everything outside the patterns above (queries built
across methods, repositories, `IQueryable` parameters, lazy loading configured in another project).

It is reported once per navigation and loop, at the first read; the related location is the query.

## Quick fix: Add .Include(x => x.Nav)

Inserts `.Include(x => x.Nav)` right after the `DbSet` of the query (the query is always in the same function, see
above) and `using Microsoft.EntityFrameworkCore;` when the file has none. The lambda parameter is the entity's
initial, or `x` when that name is taken. Like every Refyntra quick fix it is compile-checked and one undo step; *…in
document, project or solution* applies it at every result of the scope.

```csharp
foreach (var order in db.Orders.Include(x => x.Customer).Where(o => o.Total > 0).ToList())
```

Consider a projection (`Select(o => new { o.Id, CustomerName = o.Customer!.Name })`) when you only need a few
columns, and `AsSplitQuery()` when you include several collections.
